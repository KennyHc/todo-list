# #61 Reload during a large sync silently loses tasks
Status: done
PR: pending
Summary: The sync engine counts writes the server hasn't confirmed and publishes the count (`useSyncStore.pendingWrites`) after 1 s. The account menu, button label and badge then say "Saving N changes…" instead of "Synced", and `beforeunload` asks the user to stay while any write is in flight (edits still in the debounce window are flushed first). Ordinary reloads aren't nagged, and the small-edit debounce (250 ms / 1 s) is unchanged. This PR adds the warning only; full durability is a follow-up.

## What changed
- src/sync/firestoreSync.ts: `trackPending` around every `batch.commit()`, `pendingNoticeMs` option (default 1000), and a `beforeunload` guard added and removed with the engine. A stopped engine publishes nothing more.
- src/sync/status.ts: `pendingWrites` + `setPendingWrites` (optional on `SyncStatusSink`, so test sinks don't need it).
- SettingsPopover: `savingLabel`, menu status `data-status="saving"` (the dot pulses unless reduced motion), button aria-label. App: `main[data-saving]`, which shows an accent badge.
- tests/emulator/sync.test.ts: a 1,200-task restore reports a pending count > 0 that returns to 0, and the server ends with all 1,200.
- e2e/pending-writes.spec.ts (desktop): a 2,000-task restore via `__e2e.restoreTasks` shows "Saving", blocks unload while in flight, stops blocking once confirmed, and a reload keeps all 2,000.

## Tried and rejected
- A new `SyncStatus` value 'saving': `main[data-sync="ready"]` is what e2e `ready()` and the splash rely on. A separate count is less invasive.
- Publishing the count right away: every small edit would flash "Saving" for ~100 ms.

## Notes for future agents
- Follow-up (not in this PR): durability. A reload the user insists on still loses the batches Firestore hadn't queued locally. Options: write large changes in fewer, awaited steps, or persist the pending diff and replay it on load before trusting the server snapshot.
- Offline, commits never settle, so the page asks before unloading while offline with unsent edits. That is deliberate (we can't tell queued from unqueued).
