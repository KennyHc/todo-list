# #84 [QA] Undo applies its own diff, not a whole snapshot (reverts other devices' edits)
Status: done
PR: #98
Summary: Undo and redo (toast, ⌘Z, ⇧⌘Z) no longer restore a whole snapshot. Each history entry keeps the content before and after its action, and undo applies only the change after→before on top of the live state (`applyChange` in the new `src/lib/undoMerge.ts`). Other tasks and edits made since (on another device or arriving through sync) stay. Remote content no longer trims the ⌘Z history.

## What changed
- `src/lib/undoMerge.ts` (+ test): `applyChange(cur, from, to)`, a 3-way merge. Tasks merge field by field. `childIds`, `rootIds` and History merge by id, tag colours per tag, then `normalizeTree`. Unchanged parts keep their identity.
- `src/store/tasks.ts`: `UndoEntry` is `{ before, after }` (was `snapshot`). `commit(state, next)` fills in `after` for every recording `set`. `stepBack`/`redoLast` use `applyChange`, and the redo/undo entry they push records what they actually changed. Edits folded into a just-added row's add move that add's `after`. `hydrate` keeps `past`/`future`.
- `src/store/tasks.test.ts`: a new "undo after remote changes (#84)" block (QA's two-tab steps, same-task conflict, cascade, delete, History restore, add then remote edit, restored backup). The old "drops steps older than remote content" test now expects the steps to be kept.

## Conflict rule (same task)
- A field changed since the action keeps its newer value. The action's other fields are still undone (complete, then a remote rename: undo reopens the task and keeps the new name).
- A task the action created is only deleted by undo if it is unchanged since (expanding and collapsing don't count). A task deleted since stays deleted. A task the action deleted comes back.
- Child lists, rootIds and History take back the ids the action added and put back the ones it removed, next to their old neighbours. A pure reorder is only replayed if the list is unchanged since.

## Tried and rejected
- Per-task "skip if changed since": a deleted subtree came back orphaned whenever its parent or rootIds had changed remotely. Field-level merge plus `normalizeTree` avoids that.
- Dropping the entry when anything it touched changed: Undo would silently do nothing in the QA case.

## Notes for future agents
- Every `set` that records an entry must go through `commit(state, …)`, or `after` stays null and the entry can't be undone (`stepBack` skips it).
- Fields are compared by value (`sameValue`). Sync gives changed tasks new objects, so reference checks alone would see every remote touch as a conflict.
