# #58 Delete account: re-auth uses a popup in the installed PWA (same failure as #37)
Status: done
PR: #59
Summary: In an installed PWA (`isStandalone()` from `src/store/auth.ts`), Delete account re-authenticates with `reauthenticateWithRedirect` straight away (setting `DELETE_PENDING_KEY`); browser tabs stay popup-first with the redirect fallback; on return the deletion resumes only after a successful re-auth, and a cancelled or wrong-account return shows a notice that the account was not deleted instead of dropping it silently.

## What changed
- src/sync/deleteAccount.ts: `reauthenticateWithGoogle` skips the popup when `isStandalone()`; the redirect branch (pending flag set, cleared on failure) is shared with the popup-blocked fallback.
- src/store/auth.ts: `handleRedirectResult` shows `DELETE_NOT_CONFIRMED` when a delete was pending and the result is empty or errors, `DELETE_WRONG_ACCOUNT` on `auth/user-mismatch` (instead of the sign-in error on the landing page).
- Tests: deleteAccount.test.ts covers the real default re-auth (tab popup, popup-blocked fallback, both standalone checks, failed redirect clears the flag); auth.test.ts covers resume, empty return and user-mismatch.

## Tried and rejected
- Asking the user to confirm again after the redirect: they already typed the confirmation and proved who they are; resuming is what the existing popup-blocked path did, and the issue allows it.
- Moving `isStandalone` to a shared module: `deleteAccount.ts` can import it from `store/auth` (no static cycle; auth imports deleteAccount lazily). `src/pwa/install.ts` still has its own copy; merging them is a cleanup, not this issue.

## Notes for future agents
- `test:emulators` / `test:e2e` not run locally (the tester owns the emulator ports); CI runs them.
- Not verifiable on a real installed phone before deploy.
